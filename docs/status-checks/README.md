# Weekly status checks

What the teacher expects at every practical lesson until the Week 15 defence. Source: "Weekly Project Status Check and Final Goal" (course handout).
One file per week: `week-NN.md`, generated with the `status-check` skill. Final-defence answers: [`final-defence.md`](final-defence.md).

**Main goal:** by Week 15 a working information system that solves a clear problem. The scope can be small, but the main process must work from start to finish.

**Rule:** a promise is not progress. Progress must be visible and measurable. You show the result, explain it, and connect it to your own work.

## Before every lesson

- Decide the project's current stage and status.
- Prepare a short demo of what exists. Show the technical part, not only slides or ideas.
- Write what each member personally completed.
- Agree on one measurable task per member: owner, deadline, and a result that can be checked.

## What we show

| Team report | Individual report |
|---|---|
| Current stage and project health | My responsibility in the project |
| What changed since the last check | What I personally completed |
| Working feature, prototype, data model, test or other evidence | Evidence of my contribution |
| Current difficulty and team decision | What I will complete before the next lesson |
| Next team milestone | My deadline and expected result |

## Stages

| Stage | Meaning | Next step |
|---|---|---|
| Planning | Idea, but no clear scope or technical result | Confirm the problem, main process, requirements, roles, scope, first prototype |
| Started | Designs, documents, data models or functions exist, but the main process doesn't work | Build one small end-to-end process; show a visible result every week |
| Technical foundation exists | Prototype, database, architecture or separate working parts | Connect the parts, finish core functions, check data flow and roles |
| Working system | Main process works; quality, errors, security, usability or tests may be weak | Test success and failure cases, fix defects, improve security and UX |
| Finished | The agreed core product works and meets its acceptance criteria | Improve quality, testing, docs, deployment, analytics, user value |

## Status (separate from stage)

| Status | Meaning | Must show |
|---|---|---|
| On Track | The next milestone is realistic | Evidence, owner, deadline, next action |
| At Risk | A problem may affect time, scope, quality or users | Cause, impact, response, person responsible |
| Blocked | Can't continue without a decision, resource, access or dependency | Exact blocker, escalation, owner, recovery date |

## Measurable tasks (examples from the handout)

- Create the registration screen and save a new user in the database.
- Test five booking cases and record the result of each.
- Add two user roles and show what each can and cannot access.
- Prepare a deployment guide and run the system on another computer.

## Contribution

Programming is not the only valuable contribution, but every member must produce evidence and explain how it supports the system.

| Role | Measurable contribution | Must explain |
|---|---|---|
| Developer | Working feature, integration, error handling, deployment | What was built, how it works, what was tested, what trade-off was made |
| Data / database | Data model, keys, validation, queries, reports | How data moves, how integrity is protected, who may access it |
| UI / UX | User flow, prototype, accessibility, usability | Which user problem is solved, what feedback changed the design |
| Testing / quality | Test cases, defect log, acceptance or security checks | What failed, why it mattered, what changed after testing |
| Analyst / IT manager | Requirements, process model, acceptance criteria, risks | How the decision affects users, scope, quality, time, data |
| AI-assisted development | A generated feature the student reviewed, changed, tested and integrated | What AI made, what the student changed, how it was verified, what limits remain |

## What "finished" means (Week 15)

- The system solves the agreed user or organisation problem.
- The main user process works from start to finish.
- Important data can be created, stored, changed and used correctly.
- Key roles and access rules are clear.
- The main process and important error cases are tested.
- The product can be demonstrated in a stable way.
- The team can explain current limitations and future improvements.
- Every member can prove and explain their own contribution.
